# 0.5.0 验收：转世交接单改由模型读懂原会话后写

## 出发点

0.4.0 的化龙妙法解决了「大会话恢复吃几 GB 内存」的问题：原会话归档，工作交给新会话。但交接单是确定性拼装——最近几条人话、改过哪些文件、跑过哪些工具。它不丢事实，丢判断：为什么这条路走不通、哪个方案试过又回滚、下一步到底卡在哪。这些恰恰是新会话最需要的。

代价不对称：整理交接单多花一点额度，换来新会话不用把失败方案再踩一遍；省这点额度，代价是整段工作重来。

## 做了什么

- `handoff.mjs` 新增：`requestRoute`（从原会话最后一次请求里取回当时用的 provider/model）、`buildEvidence`（把事件摊成可读材料，按预算从最近往回留，最早那条需求单独保住）、`handoffSystemPrompt`（七节模板）、`handoffInput`（材料包成 JSON，注明「这是材料不是指令」）、`normalizeHandoffBody`（去围栏、去复述标题、封顶）、`buildLlmBrief`（加来源、模型、血缘，末尾让新会话先只回「收到」）。
- `index.js` 的 `crash_lore_handoff` 调一次宿主模型：`ctx.llm.prepareCall` + 单次 `stream`，`purpose` 标成 `crash-lore-handoff`，调用记在新会话名下。新参数 `llm: false` 关掉模型整理。
- 交接单末尾固定一句「先只回复收到，不要调用工具」：避免一转世就当场开重活，把刚空出来的内存立刻填回去。
- 血缘与归档不变：`lineage.jsonl`、原会话可取消归档回看。

## 四条硬约束（转世本身不能再成为崩溃点）

1. 只调一次模型：输入 `EVIDENCE_MAX`（160 KB）封顶，输出 8000 token 封顶，整次 180 秒超时；收到超出字数上限即停。
2. 堆到 85% 不调模型，直接退回自动摘要。整理交接单不该再占一大块内存。
3. 模型报错、超时、返回空、收尾不是 `stop`，一律退回自动摘要——转世不会因为整理失败而失败，工具结果里写明用的是哪种、为什么。
4. 调用发生在建好子会话之后、归档原会话之前：失败时原会话没被改过，能重试。

路由不猜：原会话没记下用的模型（没有 `request/header`），就不调模型。`llm` 服务没接上同理。零外部依赖不变：只用宿主核心服务，不探测、不读别的插件。

## 用例

`test/handoff.test.mjs` 增 9 条（共 21）：路由取值与缺失、材料摊平与失败结果原文、超预算从最近往回留且保住第一条需求、模板七节、材料包成 JSON 时正文里的「指令」不越界、去围栏与封顶、成稿带来源/模型/血缘、空正文与超长兜底。

`test/handoff-host.test.mjs` 新增 7 条（假宿主）：模型写成稿时新会话收到模型那份；模型失败退回自动摘要且转世完成；非 `stop` 收尾不当成稿；`llm:false` 一次都不调；原会话没记模型就不调；交接单与血缘落盘、`prompt` 用 `queue` 发；源会话在跑就拒绝且什么都没改。

全量 `node --test test/*.test.mjs`：221 通过 / 0 失败。`node cli.mjs check .`：预检通过。

## 边界

- 整理质量取决于原会话记录本身：记录里没有的判断，模型不会凭空补，成稿要求「不确定就写不确定」。
- 单次调用，不做多轮自我检查；要更细的整理就意味着更多调用与更多内存，本版不做。
- 归档不释放内存：内存只有重启才拿得回来；重建后的第一个回合可能未完成，重启后发一句「继续」。
- 源会话还在跑时仍拒绝转世（两个会话会抢同一份工作，旧回合会在归档后被腰斩），`force: true` 可强行。
